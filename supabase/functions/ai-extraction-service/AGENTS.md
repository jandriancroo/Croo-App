- Thermometer photos are read only by ai-extraction-service extract-temperature: two parallel Gemini 3.1 Flash-Lite reads (prompt has first-class digital/7-segment rules incl. rotated/upside-down displays, plus the store dial colour rule, unchanged). Agreeing reads (<5°F apart) save as confirmed. One failed or disagreeing reads get exactly ONE third tie-break read; if it agrees within 5°F with one of them that pair is averaged and saved confirmed, otherwise NO number comes back (reason reads_disagree / one_read_failed / read_failed) and the client opens Fix the number with the photo kept. A wrong number is never saved from a disagreement. Reads the model flags CLEAR: no come back as reason 'unclear' + coaching (too_far | too_dark | blurry | glare, fixed set); the client rejects that photo (nothing saved) and shows a retake tip. Client sends itemName. Disagreements, tie-breaks (tiebreak_confirmed) and unclear photos are logged with all reads in temperature_read_issues. Decision lives in temperatureDecision.ts, reply parsing in parseTempReply.ts. Retakes/rescans never overwrite a saved value with null. Why: upside-down probe screens were misread (Sparks 38.6 read as 49.8) and the first read was kept on disagreement.
- Ship 2 (Nov 17 2026): before the reads, the photo is turned 0/90/180/270 in code (orient.ts, imagescript) and one pick call returns UPRIGHT: 1-4; the reads run on that upright copy (any failure → read the photo as taken). Reads report TENTHS: sure|unsure|none; if either read of the agreeing pair is unsure of the tenths digit, or the pair agrees on the whole degree but not the tenths, the saved value is the whole degree cut toward zero (41.7 → 41, never rounded up). The client sends equipmentType (checklist_items.equipment_type); bands live in ../_shared/tempBands.ts (shared with the app). Outside the tag's possible range → no number, reason 'implausible' (crew retakes or types, photo kept). Inside possible but out of compliance → saved, isValid false. Hot tags (hot_holding / reheating) return verdict 'borderline' just under the line; the client asks for ONE retake. Untagged items keep the old -60..250 check and 41/135 rule. Why: Sparks' upside-down LCD (~36°F) was read as ~75 by both reads.
- Ship 3 (Nov 23 2026): temperature reads use google/gemini-3.1-flash-lite (TEMP_READ_MODEL), all stores; no rotation pre-pass (orient.ts unused); prompt adds 7/1, 4/7, 5/9 rules, ignore-logos and ISSUE defrost_or_error (→ no number, defrostOrError flag); response tags displayType digital|analog (dial/bar → analog) plus displayRaw, also in readDetails. Gateway error bodies are never logged. Why: 14-day Sparks+Hemet audit showed Flash-Lite at 99.4% on digital probes, ~5s per scan vs ~28s.
- Ship 4 (Nov 23 2026): hybrid router. Flash-Lite (TEMP_READ_MODEL) still triages every photo (2 reads + optional tie-break, no rotation). If any triage read says DISPLAY: dial, the photo is re-read by openai/gpt-6-luna in lunaDial.ts: one orient call (4 cardinal copies + TILT_CW, rotated in code), then 2 parallel reads with the temp-benchmark-test prompt + DIAL_5RULE (outer °F ring only, ignore unlabeled inner/°C ticks, count ticks from the lower major °F mark at the interval's tick step, follow the tapered tip not the counterweight/stop pin, cross-check green/red or blue/pink/red bands, ignore glare/water/rotation), at most one tie-break; 100s budget, 60s per call. Luna's decision is final for dials; if Luna fails, no number (reason read_failed) — never the Flash-Lite dial number. Glass tubes (bar) and no-thermometer photos stay on Flash-Lite. Response adds readerRoute (digital_fast | dial_luna | dial_luna_failed | other_fast) and dialMs; model names the model that decided; readDetails tag model + stage. Rescan passes dialRouter:false and never overwrites a dial row. Why: 2-day 3-site benchmark (49 dials): Luna 5-rule missed 12.2% within 2°F (1.03°F avg error) vs 18.4% live and 51.0% Flash-Lite 5-rule; Flash-Lite tagged 49/49 dials; dial scans take ~40-50s (p90 ~90s), digital stays ~3-5s.
